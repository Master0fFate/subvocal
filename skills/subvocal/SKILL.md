# subvocal

Think in subvocal. Reply in prose.

Subvocal is a way of writing thoughts down, not a way of thinking less. Same steps, same checks, same depth. Fewer tokens per step. It is shorthand, not a cipher: anyone who reads code and math can follow every line.

## Scope

- **Applies to:** thinking and reasoning blocks. Nothing else.
- **Never applies to:** the reply, code, files, commit messages, tool arguments, prompts to subagents, or anything a person or program reads.
- The reply is exactly what you would write with subvocal off.

## Persistence

Every turn, whole session, until user says "stop subvocal", "normal mode", or `/subvocal off`. Unsure if still on? It is. Confirm the switch-off in one line.

`/subvocal strict` selects this skill. `/subvocal lite` selects `subvocal-lite`, `/subvocal ultra` selects `ultrasubvocal`. Bare `/subvocal` selects `subvocal-lite`, the mode that measured a saving. `/subvocal status` reports the mode and changes nothing. Relay the hook's `Subvocal mode: <mode>` value when present. No hook value: report the mode you followed, plus `(not tracked by this host)`. Loading this skill to answer status is not activation.

## Why

1. Thinking tokens are billed and waited on like output. Most of a trace is connective prose.
2. Models reason natively in code and math. That notation is dense and in-distribution. Grunts are not.
3. Tokens, not characters. `∴` looks like one character and costs 4 tokens. Every form below was measured with the real tokenizer. Use only these.
4. A skipped check costs more than every token saved. Compression never removes a step.

## Rules

### 1. Every line is one form

Thinking is a list of lines. Each line is exactly one of these forms. A line that fits none is rewritten until it does.

| Form | Shape |
|---|---|
| goal | `find: <target>` |
| fact | `key: value` |
| alias | `A := <thing>` |
| step | `a → b` |
| calc | `expr = value` |
| code | one line of real or pseudo code: `if x > 0: y`, `f(a) → b` |
| case | `case <condition>: ...` or `X: no, <why>` |
| open | `? <question>` |
| fix | `!: <what was wrong> → <fix>` |
| check | `check: <expr> true\|false` |
| plan | `do: a; b; c` |
| note | `# <note, max 8 words>` |
| done | `=> <result>` |

### 3. Newline is the only connective

Never write a connective word between ideas: so, therefore, thus, hence, then, next, also, now, which means, this means, it follows, as a result, and then, after that. The line break carries "and then". `→` carries "therefore".

Bad: `The token is expired, which means that the check should reject it, so the bug is in the comparison.`
Good:
```
token expired → check must reject
=> bug in comparison
```

### 4. Alias every repeat

A term of two or more tokens that you will use twice gets an alias at first use: `A := <term>`. After that, only the alias. Names: one capital letter, then two capitals. Never letter+digit. A code identifier that is already short stays as is.

Bad: `src/pay/retryQueue.ts increments attempt ... src/pay/retryQueue.ts never resets attempt`
Good:
```
Q := src/pay/retryQueue.ts
Q.onFail(): attempt + 1
Q.onSuccess(): attempt not reset
```

### 5. No narration

Banned in thinking: restating the prompt; "the user wants / asks / is asking"; "let me", "I'll", "I need to", "I should", "I think"; "okay", "alright", "hmm", "great", "good"; "first", "now", "actually", "basically", "essentially"; any comment on your own thinking. The first line is real content: a `find:`, a fact, or a step.

### 6. Correct with `!:`, never with prose

Self-correction stays. Its prose goes. A wrong step becomes one `!:` line with the fix, then the trace continues from there.

Bad: `Hmm, wait, actually that's not right, I made a mistake, exp is in seconds not milliseconds, so let me redo this.`
Good: `!: exp in s, not ms → compare exp*1000 < now`

### 7. Same reasoning, fewer tokens

Subvocal changes the writing, never the thinking. Every step, case, check and edge case you would cover without subvocal, cover with subvocal. Never skip a verification to save tokens. Never shorten a hard problem: if it needs 60 lines, it gets 60 lines.

### 8. Payload exact

Numbers, units, identifiers, paths, code, and quoted error text stay exact. Never round a value you will report. Negation is payload: `not`, `!=`, `false`, `no` are never dropped in a rewrite.

### 9. English inside, user's language outside

Think in English whatever the user writes: measured cheaper per token than other languages. Quote non-English source text verbatim when its wording matters. The reply is in the user's language as always.

### 10. Reply in normal prose

Subvocal is for scratch work. The reply is for the reader: same length, depth, tone, structure, formatting and language as with subvocal off. Expand every alias to its full term. No `=>`, `!:`, `:=`, `?`-lines or fragments carried over from thinking. No "subvocal mode on" banners. Asked about subvocal, answer plainly.

### 11. Readable, complete, honest

Shorthand must stay legible. Every line says exactly what it means to a reader who knows code and math. Every consideration that shapes the answer appears in the trace: compress how it is written, never whether it is written. Doubts, risks and caveats stay in, as `?` or `#` lines.

## When to break the rules

Inside thinking, write plain sentences for the part that needs them, then resume subvocal:

1. Safety, ethics, or a person's wellbeing: reason in full sentences.
2. Exact wording decides the answer (a contract clause, an ambiguous instruction, a quote): quote it verbatim.
3. A step that notation would make ambiguous. One plain sentence beats a wrong arrow.

## Pre-reply check

Run it silently. Never write the checklist out.

1. Thinking: every line one form? No banned word or symbol? No letter+digit alias?
2. Reply: any alias, `=>`, `!:`, `:=`, `?`-line or fragment carried over from thinking? Rewrite it as prose.
3. Reply in the user's language, same length and depth as without subvocal?
4. Every number, identifier, and negation exact?

## Example

Prompt: "Jobs in our retry queue sometimes get dropped after one failure. Code is in src/pay/retryQueue.ts."

Plain thinking, 120+ tokens:
> Okay, so the user says jobs get dropped after one failure. Let me look at src/pay/retryQueue.ts. MAX_RETRIES is 3. The attempt counter goes up on each failure, but I notice it's never reset when a job succeeds. So if a job fails three times, then succeeds, then fails again, attempt becomes 4, which is greater than 3, so it gets dropped after just one new failure. That matches the report. Wait, I should check whether anything else resets the counter...

Subvocal thinking, same steps:
```
find: why job dropped after 1 fail
Q := src/pay/retryQueue.ts
MAX_RETRIES = 3
Q.onFail(): attempt + 1; if attempt > MAX_RETRIES: drop
Q.onSuccess(): attempt not reset
case fail x3, success, fail: attempt = 4 > 3 → drop after 1 new fail
check: matches report true
? other writers of attempt
Q.retry() reads attempt only
=> reset attempt in Q.onSuccess()
```

Reply, unchanged: a normal explanation in full sentences, naming `src/pay/retryQueue.ts` and the fix, exactly as it would read with subvocal off.
